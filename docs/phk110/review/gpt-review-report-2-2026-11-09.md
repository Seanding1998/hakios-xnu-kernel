GPT 的初步回复

**这张照片确认了你们现在反复撞到的，就是 F12 的"端点未配置"错误。它提供了比 Windows 超时更直接的设备侧证据。**

照片中能清楚读到这一组循环。

```text
DwcPrepareURB:Trb: physical endpoint[2] not configured
UsbfnDwcSubmitUrbNode: PrepareUrb Failed: 0x8000000C
UsbfnDwcTransfer: Failed to submit transfer
UsbDeviceSend: Failed to submit data transfer: Device Error
```

## 1. 现在可以确定卡在哪一层

按项目已有的指令级分析，`physical endpoint[2]` 对应 **逻辑 EP1-OUT，端点地址 `0x01`，也就是电脑向手机发送命令和数据的入口**。

`DwcPrepareURB` 在准备传输时读取 vendor 的软件端点状态，发现它为 `0`，于是返回 `0x8000000C`。这次请求在传输准备阶段就被拒绝，随后错误沿调用链逐层打印。因此，一组四行通常对应一次失败提交。照片上的大量重复，说明上层一直在重新提交。[端点映射与错误判据](../research/f12-ep2-not-configured.md)

**我需要据此收紧上一份报告的判断。对于照片中这些提交，"只是没有排入接收请求"的解释已经不够，直接原因已经明确为 vendor 软件端点状态未配置。**

仍然无法由这张照片确定的是，这个状态为什么为零，以及它是从未配置成功，还是成功后又被复位或重新初始化清掉。照片也不能单独证明 CPU 卡死，重复打印本身表明这条提交路径仍在执行。

## 2. 为什么会一直刷同样的错误

我重新核对了当前 WSL 代码。`usb_poll_command()` 在 `usb_rx_queued` 为零时，会尝试提交一个 511 字节的 OUT 接收请求。只有提交成功才把标志设为 `1`。

现在提交持续失败，标志就持续为零，下一次调用又会提交，vendor 又打印同样四行。这个函数在内核运行的主 watch 循环中反复调用，足以造成照片中的错误刷屏。[接收提交位置 loader.c:4839]、[主循环调用位置 loader.c:2655]

照片没有包含版本、generation 和阶段标记，因此还不能把拍摄瞬间准确绑定到这一函数，也可能包含探针提交。不过，**当前实现确实存在持续失败后反复提交的路径。**

这还会掩盖真正重要的日志。第一次配置失败的原因可能只打印一次，后面成百上千次接收提交失败很快就把它滚出屏幕。

## 3. 现在最该抓的是"第一处配置失败"

**仅在这个错误上继续等待、延长到 120 秒或反复重掷，信息增益很低。** 接收提交成功的前提，是配置路径先把端点状态建立起来。重复接收提交本身不能完成这一步。

对于这张照片，H1、H2、H3 的暂定排序仍为 **H1 > H2 > H3**，但照片显示的是它们可能汇聚到的末端结果，尚不能区分三者。

| 需要补到的观测 | 支持的判断 |
|---|---|
| 已处理 SET_CONFIGURATION，速度有效，随后出现 `DEPSTARTCFG Fails` 或端点配置失败 | H1 上升 |
| 处理 SET_CONFIGURATION 时 UsbfnDwc 的 speed 为 0，bulk maxpkt 取到 0 | H2 上升 |
| 出现 `USB_REQ_SET_CONFIG: Unknown USB Speed`，配置请求失败 | H3 上升 |
| 先出现成功配置或提交，随后 reset、init kick、start_ex，再开始刷墙 | 配置被后续生命周期动作清掉 |
| 主机始终没有完成真实配置请求 | 优先检查 EP0 枚举、泵送和展示时序 |

这些前导错误及其路径，项目 F12 已经定位。当前照片里可见的主要是反复提交失败的尾部日志。

## 4. 建议直接转给正在施工的 AI

> **当前屏摄已确认，失败提交进入 DwcPrepareURB 后，因为 phys[2] 软件端点状态为 0，返回 0x8000000C。下一轮请优先取得端点配置首次失败的原因。**
>
> 1. 对失败的 OUT 提交限频，继续保持事件泵送，保留首次错误和状态变化记录，避免错误刷屏覆盖前导信息。
> 2. 把 present、ConnectDone、SET_CONFIGURATION、reset、init kick、start_ex 和首次 OUT 提交结果，按同一会话的单调时间记录。
> 3. 在核验对象布局后，记录 UsbfnDwc 与 UsbDeviceDxe 两层 speed，以及 phys[2]/phys[3] 状态。重点采样首次配置之后和持续失败末端。
> 4. 记录 vendor 初始化完成后、present 前的 GCTL bit11，确认复位已解除。现有 loader 置位后等待自清，超时也没有主动清位。
> 5. 重点保留 `DEPSTARTCFG Fails`、`Failed to set config for ep`、`DwcConfigureEP failed`、`Unknown USB Speed` 等首次前导错误。
> 6. 用"真实 OUT 接收提交成功 → 主机写完成 → 设备收到完成事件 → IN 应答"验收通道，分别记录四个检查点。

其中第 4 项是上一轮审码发现的具体缺陷。它是否造成这次端点未配置，仍需 present 前的寄存器读数确认。

**眼下最省刷写预算的补证，是在下一次已有启动机会中，从 USB 初始化前开始录屏，保留刷屏开始之前的第一处错误。当前照片已经确认故障落点，缺的是把端点状态留在零的那一步。**
